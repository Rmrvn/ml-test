# Avito: кандидатогенерация для поиска услуг

Тестовое задание на стажировку ML-инженера. Нужно по короткому запросу («автоподбор», «баня на дровах») выбрать из корпуса до 50 объявлений, которые потом пойдут на ранжирование. Метрика Recall@50.

**Итог на платформе: Recall@50 = 0.7785.** Отправляла три раза: 0.7382 → 0.7443 → 0.7785. Каждое улучшение появилось после разбора ошибок, о нём ниже.

## Что в репозитории

- `solution.ipynb`: всё решение целиком: EDA, эксперименты, разбор ошибок, финальный инференс;
- `answer.csv`: файл, который я сдала (его создаёт последняя ячейка ноутбука);
- `requirements.txt`: зависимости.

## Как запустить

1. Скачать данные по ссылке из условия и положить в папку `data/` (`train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet`). В репозиторий я их не добавляла, они слишком большие.
2. `pip install -r requirements.txt`
3. Выполнить `solution.ipynb` сверху вниз. В конце ячейка сама проверит формат ответа.

Всё работает локально, внешние API не нужны.

## 1. Какие данные и признаки я использовала и почему

Сначала я посмотрела на данные, и это сильно повлияло на решение. Три главных наблюдения:

- **Id объявлений в train и в корпусе бенчмарка почти не совпадают:** общих только 18 142 из 189 212, около 5%. Поэтому идея «посмотреть, какие item_id кликали по такому запросу раньше» не работает, и искать пришлось по содержимому объявлений.
- **В train нет `query_id`.** Я восстановила запросы группировкой по всем колонкам `search_*` и получила 354 463 уникальных запроса. У 85% из них ровно одно релевантное объявление.
- **Больше всего помогает локация.** В 83% релевантных пар локация запроса совпадает с локацией объявления.

Также выяснилось, что `item_category_id` почти всегда равен одному значению (99.997%), поэтому я его не использовала.

**Признаки, которые вошли в решение:**

- заголовок и параметры объявления, приведённые к основам слов (текстовое совпадение с запросом);
- совпадение локации запроса и объявления;
- **соседние локации:** из train я посчитала, в каких локациях пользователи из данной локации реально выбирали объявления. Оказалось, что у 64% запросов, у которых нет совпадения по локации, в их собственной локации нет вообще ни одного объявления, и без такой таблицы нужное объявление просто не находится;
- теги «Вид услуги» и «Тип услуги» из текстовых параметров запроса и объявления. Они не зависят от train, поэтому работают и на новых запросах. Покрытие 61.5%, а когда теги есть у обоих, они совпадают с релевантным объявлением в 97.9% случаев;
- подкатегория (`item_microcat_id`) через словарь «текст запроса → самая частая подкатегория». Признак слабый, вес у него маленький (0.05).

**Что я попробовала и не стала использовать:** рейтинг и число отзывов (это скорее про качество объявления, чем про релевантность, прироста не дало), описание объявления (длинное и шумное) и расстояния между локациями по координатам (их заменила таблица соседей, полученная из поведения пользователей).

## 2. Какие модели и алгоритмы

Что тут важно:

- **Текст.** Стемминг Snowball из `nltk` и TF-IDF с биграммами. Включила `sublinear_tf` и `max_df=0.3`, чтобы отсечь шаблонные фразы вроде «Начальная цена», которые есть почти в каждом объявлении.
- **Соседи.** Буст линейно уменьшается с рангом соседней локации: чем чаще из этой локации выбирали объявления в соседней, тем сильнее буст.
- **Теги.** Значения тегов ищу по списку известных меток. Метки пришлось отсортировать по длине, иначе короткое «Тип услуги» перехватывало «Тип услуги автосервиса» (классическая ловушка regex-альтернации).
- **Резерв.** Если по тексту ничего не нашлось, беру объявления из той же локации, а если и их нет, топ по рейтингу. Так каждый `query_id` получает ответ.
- **Веса.** Перебирала на сетке из 27 комбинаций, и результат оказался на плато (0.7685-0.7690). Я взяла значения из середины плато, а не из точки максимума, чтобы не подгонять под шум.

Библиотеки: `pandas`, `numpy`, `scipy`, `scikit-learn`, `nltk`.

## 3. Как я проверяла качество

- **Валидация.** Свернула train в уникальные запросы и отложила 5% (17 724 запроса). Искала среди объявлений train. Таблицу соседей и словарь подкатегорий строила только по train-части, чтобы не было утечки.
- **Быстрые эксперименты.** Полный прогон на валидации занимает около 4 минут, поэтому для перебора я взяла фиксированную подвыборку из 3000 запросов (около минуты на прогон). Про это пришлось узнать на практике: перебор весов на полной валидации занял 108 минут, и после этого я всё быстро проверяла на подвыборке.
- **Как росла метрика на валидации:**

| Шаг | Recall@50 |
|---|---|
| TF-IDF по заголовку | 0.1485 |
| + стемминг и `max_df` | 0.1797 |
| + подкатегория | 0.1837 |
| **+ локация** | **0.7632** |
| + `sublinear_tf` | 0.7661 |
| + теги | 0.7687 |

Соседние локации проверяла на подвыборке 3000: recall вырос с 0.7577 до 0.8232.

- **Проверка формата** перед отправкой: одна строка на каждый `query_id`, не больше 50 id в строке, без повторов, id из 16 символов `0-9a-f` и все есть в `benchmark_items`.
- **Отправки на платформу.** Три попытки, метрика росла так же, как на валидации: 0.7382 → 0.7443 (добавила теги) → 0.7785 (добавила соседей).

**Что я пробовала и отказалась:**

| Эксперимент | Что получилось | Почему отказалась |
|---|---|---|
| Символьные n-граммы | recall 0.1376, преобразование заняло 877 с | Дольше и хуже, чем слова |
| Эмбеддинги MiniLM (`paraphrase-multilingual-MiniLM-L12-v2`) вместе с TF-IDF | Только эмбеддинги: 0.4945; гибрид: +0.0014 | Прирост слишком мал для усложнения и рисков воспроизводимости |
| Буст по рейтингу | Прироста нет | Не включила |
| 20 и 30 соседей вместо 10 | +0.003, на уровне шума | Оставила 10 |

## 4. Какие ошибки нашла и что с ними сделала

Разбила потери по группам на подвыборке из 3000 запросов (recall 0.8232):

| Группа | Доля запросов | Recall |
|---|---|---|
| Та же локация | 80% | 0.890 |
| Локация-сосед | 15.6% | 0.705 |
| Другая локация | 4.6% | 0.051 |

Типы ошибок и что с ними получилось:

1. **Локации.** У части запросов в их собственной локации нет нужных объявлений. Сначала добавила буст своей локации (огромный скачок), потом буст локаций-соседей из логов train. На платформе он дал +0.034.
2. **Разница между валидацией и бенчмарком.** Словарь подкатегорий покрывал 87% запросов валидации, но только 37% запросов бенчмарка: он просто не обобщается на новые тексты. Я снизила вес до 0.05 и добавила теги, которые парсятся прямо из параметров и не зависят от train.
3. **Синонимы.** TF-IDF не понимает, что «перевозки» и «грузоперевозки» близки по смыслу. Пробовала эмбеддинги, но выигрыш оказался слишком маленьким.
4. **Конкуренция внутри большой локации.** Медианная локация содержит 2055 объявлений, максимум 26 663, и нужное объявление не всегда попадает в топ-50. Это я не решила, это главный резерв для улучшения.
5. **Шум в разметке.** Часть кликов случайна, с этим ничего не поделать.
